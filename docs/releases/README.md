# 发行说明的写法与约定

发版文案存在这个目录里，按频道与版本号分文件：

```
docs/releases/
  main/0.1.0.md    稳定版（main 分支与 hotfix/* 分支）
  dev/0.1.0.md     开发版（dev 及其余所有分支）
```

流水线按当前分支推导频道、按 `app/src-tauri/tauri.conf.json` 的 `version` 取文件，
一份文案同时喂给两处：

- GitHub Release 的正文
- `latest.json` 的 `notes` 字段 —— 它会原样显示在用户点「检查更新」后的弹窗里

所以这是给用户看的东西，不是 changelog 的副本。

只有 `main` 频道会走到这两处：开发版不做自更新，流水线拒绝为 dev 频道创建 Release，
dev 的文案只跟着 Actions 产物走，装机靠手动下载。

## 硬性规则

1. **发版前必须先有文案。** 文件缺失或内容为空，流水线直接失败，不给占位文本兜底。
   把「忘了写说明」留到用户那边才暴露，代价远高于构建挂掉。
2. **文件名就是版本号**，形如 `0.2.0.md`、`1.0.0-beta.1.md`，和 `tauri.conf.json` 里那个字符串一模一样。
   改版本号用 `node scripts/version.mjs set 0.2.0`，别手改三处。
3. **不用 Markdown 标题（`#`）。** 客户端更新弹窗是纯文本渲染，`##` 会原样显示成井号。
   分段用空行，条目用 `- `，需要小标题就写成独立一行的短句加冒号。
4. **不用 Emoji。** 全仓通行的规矩。
5. **写变化，不写实现。** 「Mod 安装会自动补齐前置依赖」是文案，「重构 install_mod 为批量计划」不是。

## 频道差异

`main` 面向普通玩家：只讲他们能感知的变化，不提内部结构。

`dev` 面向愿意吃螃蟹的人：可以写清楚哪些能力还没打磨完、已知会出问题的地方，
让人装之前有预期。开发版的「已知问题」段落尤其别省。

开发版拿不到自更新，所以这份文案只会出现在 Actions 产物里给自己人看；
真要让谁装上，把包连同这份说明一起发给他。

## 模板

```
Aurora 0.2.0

这个版本主要做了什么，一两句话讲完。

新增：
- 条目一
- 条目二

修复：
- 条目一

已知问题：
- 条目一
```

## 本地自查

```bash
node scripts/release-notes.mjs resolve dev
```

打印将要采用的频道、版本号与文件路径；文案缺失时以非零码退出。想直接看内容用 `print`。
